# 同步/异步 与 阻塞/非阻塞 详解（两个维度、四个象限）

> 存放位置：`basic\chapter11\md\同步异步与阻塞非阻塞详解.md`
> 前置知识：`time.sleep` 与耗时直觉、多线程基础（chapter10）、协程 / `await`（本章其他文档）、I/O 与 socket 概念
> 配套验证：本文所有耗时数字均在 `D:\python\fastapi_test\.venv`（Python 3.13）实测

## 一句话结论

**这两对词描述的不是同一件事，而是两个正交的维度：**

- **同步 / 异步**：回答"**结果怎么回来**"——调用方自己等结果（同步只约束一件事：结果由调用方自己获取（没有别人通知你）。它不约束你用什么方式等待：可以挂起等（阻塞），也可以反复询问、期间做别的事（非阻塞轮询）。后者就是 “同步非阻塞”。），还是调用立刻返回一句"办好了通知你"（回调 / Future / 事件）。
- **阻塞 / 非阻塞**：回答"**等的时候线程在干什么**"——线程被操作系统挂起（让出 CPU 但不能干别的），还是调用立刻返回（线程继续跑）。

所以它们能组合出四种状态，最经典的是**"异步阻塞"（select/epoll 等事件）**——听起来矛盾，但真实存在。**把两者混为一谈，就会以为"异步 = 不阻塞"，这是最常见的误解。**

同理，**"同步必然阻塞"也不成立**：同步只规定"结果由调用方自己拿"，不规定拿的时候线程是睡着还是转着——非阻塞 socket + 轮询就是"同步但完全不阻塞"（详见 2.6 的实测）。

## 1. 为什么容易搞混

日常语境里我们常说"异步就是不等、不阻塞"，把四个词压成了一个意思。但严格定义下它们分属两层：

| 维度 | 描述对象 | 提问方式 |
|---|---|---|
| 同步 / 异步 | **通信机制**：结果/消息如何交付 | "调用发起后，谁负责把结果送回来？" |
| 阻塞 / 非阻塞 | **调用方（线程/进程）状态**：等待期间是否被挂起 | "等待的这段时间，这个线程还能不能干别的？" |

打个生活比方：

- **同步**：你去餐厅点菜，站在窗口等到菜做好，端走。（结果由你自己等来）
- **异步**：你点完菜拿个取餐号（Future）回座位，炸好了叫号器响你去取。（结果由对方通知）
- **阻塞**：等的时候你**寸步不离**站在窗口，什么都干不了。
- **非阻塞**：等的时候你可以**先去做别的**，偶尔回来瞄一眼"好了没"（轮询）。

于是一个人可以"拿了号却坐在门口死等"（**异步阻塞**），也可以"站在窗口但每隔 10 秒探头问一句"（**同步非阻塞，即轮询**）。**行为和机制可以自由组合**，这就是四个象限的来源。

## 2. 四个词逐个拆开

### 2.1 同步（synchronous）

**定义**：调用发出后，调用方必须**等到结果产生**才能继续执行；结果由这次调用**自己返回**。

```python
def get_data():
    time.sleep(1)      # 等 1 秒
    return "data"      # 结果由 return 直接交给我

result = get_data()    # 我必须原地等它 return
print(result)          # 等到之后才能往下走
```

特征：**"调用—返回"是一条连续的线**，中间调用方无法脱身。

### 2.2 异步（asynchronous）

**定义**：调用发出后**立即返回一个"凭据"**（Future / Task / 句柄 / 回调注册），真正的结果稍后通过**回调、事件通知或轮询这个凭据**交付；调用方不必原地等。

```python
async def get_data():
    await asyncio.sleep(1)
    return "data"

async def main():
    task = asyncio.create_task(get_data())   # 立即返回 Task（凭据），不等
    print("我先干别的")
    result = await task                       # 需要结果时才回来等/取
```

特征：**"发起"和"取结果"被拆成两步**，中间可以插别的活。

> 注意：`await` 表面像"等"，但它的作用是"**挂起当前协程、把控制权交还事件循环**"，让别的事件得以处理——这正是异步的关键。

### 2.3 阻塞（blocking）

**定义**：调用期间，**发起调用的那个线程**被操作系统挂起（进入 sleeping/wait 状态，不占 CPU），直到条件满足才被唤醒。

```python
sock.recv(1024)        # 阻塞：内核把线程挂起，直到数据到达
time.sleep(3)          # 阻塞：线程睡 3 秒，CPU 让给别人
```

特征：**线程状态 = 挂起**；等待期间该线程不能执行任何别的代码（除非别的线程替它干）。

#### 2.3.1 阻塞的主体到底是谁？

一句话：**主体是"发起调用的那个执行流"——在传统程序里就是当前线程**。不是进程，也不是函数或 socket。

| 层次 | 是谁 | 说明 |
|---|---|---|
| **引发者** | 系统调用 / 同步原语 | `read`/`recv`/`accept`/`sleep`/`Lock.acquire`——阻塞发生在这些**调用**里 |
| **承受者** | **发起调用的线程** | 被操作系统移出调度队列，进入挂起状态，CPU 让给别人 |
| **不是谁** | 不是进程、不是函数、不是 socket | 函数不会"阻塞"；socket 只有阻塞/非阻塞**模式**，没有"阻塞属性" |

所以精确的说法是：**"在阻塞模式的 socket 上调用 `recv`，会阻塞调用它的那个线程"**，而不是"socket 是阻塞的"。

#### 2.3.2 实测：阻塞只按住当前线程

**场景 1（多线程，主线程睡 1.2s，worker 线程照常打印）：**

```python
import threading, time

t0 = time.perf_counter()
def worker():
    for i in range(3):
        time.sleep(0.3)
        print(f"  [worker] 第{i+1}次 @+{time.perf_counter()-t0:.2f}s")
t = threading.Thread(target=worker); t.start()
print("[main] 开始 sleep(1.2)，主线程被挂起 @+0.00s")
time.sleep(1.2)
print(f"[main] 睡醒了 @+{time.perf_counter()-t0:.2f}s")
t.join()
```

```
[main] 开始 sleep(1.2)，主线程被挂起 @+0.00s
  [worker] 第1次 @+0.30s
  [worker] 第2次 @+0.60s
  [worker] 第3次 @+0.90s
[main] 睡醒了 @+1.20s
```

主线程被挂起 1.2 秒，worker 在 0.30/0.60/0.90 秒照常打印——**阻塞只掐住"发起调用的那个线程"，不是整个进程**。

**场景 2（asyncio 单线程，一个协程阻塞，整个事件循环停摆）：**

```python
import asyncio, time

t0 = time.perf_counter()
async def bad():
    print(f"  [bad] time.sleep(0.6) @+{time.perf_counter()-t0:.2f}s")
    time.sleep(0.6)                  # 阻塞整个事件循环所在的线程
async def ticker():
    for i in range(3):
        print(f"  [ticker] tick{i} @+{time.perf_counter()-t0:.2f}s")
        await asyncio.sleep(0.2)
async def main():
    await asyncio.gather(ticker(), bad())
asyncio.run(main())
```

```
  [ticker] tick0 @+0.00s
  [bad] time.sleep(0.6) @+0.00s
  [ticker] tick1 @+0.60s     ← 本该 0.20s
  [ticker] tick2 @+0.81s     ← 本该 0.40s
```

事件循环就跑在**这一个线程**上：`bad` 里的 `time.sleep` 让该线程被内核挂起 → 该线程上的**所有协程**一起停摆。

#### 2.3.3 不同执行模型下，"阻塞"的影响范围

| 模型 | 一个执行流阻塞，谁受影响 | 原因 |
|---|---|---|
| 单线程程序 | **整个程序停住** | 只有一个执行流 |
| 多线程 | **只卡那一个线程**，其他线程照常 | 场景 1 |
| asyncio（单线程事件循环） | **整个 loop 停摆**，所有协程排队 | 场景 2 |
| 多进程 | **只卡那一个进程** | 进程间独立地址空间、独立执行流 |
| FastAPI `async def` | 所有请求排队（loop 被卡） | 见第 7 节 |
| FastAPI `def` | 只占线程池里一个线程 | FastAPI 自动丢进线程池 |

#### 2.3.4 两个容易漏的细节

**① GIL 与阻塞不是一回事**

- `time.sleep` 会**释放 GIL** → 其他线程能正常跑（场景 1 已证明）；
- CPU 密集死循环**不释放 GIL** → 其他线程是"**抢不到**"，而不是"被阻塞"。

前者是线程**主动让出**（挂起），后者是线程**被动等调度**（可运行但拿不到执行权）——现象都像"卡住"，机制完全不同。

**② 协程的"阻塞"最终会落到线程上**

协程是**线程内部的用户态执行流**：

- `await asyncio.sleep(...)`：协程让出，线程继续跑其他协程（不是阻塞）；
- `time.sleep(...)`：协程没有让出，**线程自己被内核挂起** → 连累整个线程上的所有协程。

#### 2.3.5 一句话

> **阻塞描述的是"一次调用把它所在的执行流按住了"。执行流的最小单位是线程；协程是线程内的子执行流，它做了阻塞动作时，被按住的仍然是它所在的线程。**

### 2.4 非阻塞（non-blocking）

**定义**：调用**立即返回**——要么带结果，要么返回"还没好"的错误码（如 `EWOULDBLOCK` / `None`），线程继续往下跑。

```python
sock.setblocking(False)
try:
    data = sock.recv(1024)     # 立即返回
except BlockingIOError:        # 没数据 → 立刻告诉我，别让我等
    data = None                # 我可以先干别的，过会再来试
```

特征：**线程状态 = 可运行**；但"立即返回"不代表"结果已就绪"，需要自己想办法知道何时就绪（轮询，或交给 select/epoll 通知）。

### 2.5 一张表看清差异

| | 同步 | 异步 |
|---|---|---|
| **发起后** | 必须等到结果才返回 | 立即返回凭据 |
| **结果交付** | 本次调用 `return` 给我 | 回调 / 事件 / Future 通知我 |
| **调用方自由** | 无（除非多线程帮忙） | 有（可以先去处理别的事） |

| | 阻塞 | 非阻塞 |
|---|---|---|
| **线程状态** | 挂起（不占 CPU） | 可运行（继续执行） |
| **返回时机** | 条件满足才返回 | 立即返回（含"未就绪"） |
| **典型** | `time.sleep`、阻塞 `recv`、`requests.get` | `setblocking(False)`、`asyncio.sleep` |

### 2.6 常见错觉："同步必然阻塞"？

**不必然。** 说这话的人通常把两个不同的"阻塞"压成了一个词：

| 说法 | 含义 | 属于哪套语言 |
|---|---|---|
| **逻辑阻塞** | 代码卡在这一步，后面的逻辑走不下去 | 程序逻辑层面（口语） |
| **线程阻塞** | 操作系统把线程挂起（进入 wait/sleep，让出 CPU） | **术语里的"阻塞/非阻塞"专指这个** |

**同步只约束一件事：结果由调用方自己获取（没有别人通知你）。** 它**不约束**你用什么方式等待：可以**挂起等**（阻塞），也可以**反复询问、期间做别的事**（非阻塞轮询）。后者就是"**同步非阻塞**"。

#### 实测：同步也可以完全不阻塞

```python
import socket, time

srv = socket.socket(); srv.bind(("127.0.0.1", 0)); srv.listen(5)
addr = srv.getsockname()
c = socket.socket(); c.connect(addr)          # 客户端连上但不发数据
conn, _ = srv.accept()
conn.setblocking(False)                       # 非阻塞

t0 = time.perf_counter(); spins = 0
while time.perf_counter() - t0 < 0.5:         # 干等 0.5 秒
    try:
        conn.recv(1024)                       # 立即返回
    except BlockingIOError:
        spins += 1                            # 没数据？记一圈，接着转
print(f"非阻塞轮询 0.5s 转了 {spins} 圈")
```

实测输出（Python 3.13）：

```
A 同步非阻塞轮询: 0.5s 内转了 114341 圈 -> 线程完全没被挂起
B 同步阻塞(超时0.5s): 0.5s 内只发起了 1 次调用，期间线程被挂起
```

同一件"等数据"的事：

- **阻塞版**：0.5 秒只发起 **1 次**调用，线程被内核挂起，CPU 让给别人；
- **非阻塞版**：0.5 秒线程转了 **114341 圈**，CPU 一直没停，线程**从未挂起**。

两者**都是同步**（数据仍是自己 `recv` 拿的，没有别人通知），但线程状态一个挂起、一个飞转。**所以"同步 = 阻塞"不成立。**

#### "等"的三种姿态

| 姿态 | 线程状态 | CPU | 所属象限 |
|---|---|---|---|
| **挂起等**（睡） | 挂起，让出 CPU | 不占 | ① 同步阻塞 |
| **做别的事 + 轮询**（忙等） | 可运行，反复试探 | 烧 CPU | ② 同步非阻塞 |
| **根本不等**（事后通知） | 可运行 | 不烧 | ④ 异步非阻塞 |

#### 生活类比把差别放大

- **同步阻塞**：站在餐厅窗口，一动不动等菜做好；
- **同步非阻塞**：还是站在窗口（没人给你取餐号），但每 2 秒探头问一句"好了吗"，间隙吃口小菜；
- **异步非阻塞**：拿号回座位，菜好了叫号器响——**你不用问**。

关键区别：**同步时，你一直在那里"亲自盯着"结果；非阻塞只说明"每次探头"不会把你钉在原地。**

#### 直觉的另一半是对的

如果把"阻塞"理解为"**程序没别的事可干、只能干等这件事**"，那同步确实大多会阻塞——**当轮询期间没有别的活可做时**，轮询就是纯 CPU 空转，比阻塞还糟（阻塞至少把 CPU 让出去）。这也正是 `select/epoll`（③ 象限）存在的理由：**用一次"挂起等事件"换掉 N 次"空转轮询"**，省下 CPU。

所以准确的表述是：

> **同步/异步 = 结果由谁交付（自己拿 vs 对方通知）；阻塞/非阻塞 = 等待时线程是否被挂起（睡 vs 转）。**
> "等"有三种姿态：挂起等、做别的事并轮询、根本不等。

#### 学术根源：为什么大家总觉得"同步=阻塞"

Stevens《UNIX 网络编程》把 I/O 分了五种模型，其中**前四种都归入"同步 I/O"**：

| 模型 | 归为同步的原因 | 线程状态 |
|---|---|---|
| 阻塞 I/O | 最后要自己 `recv` 把数据搬走 | 挂起 |
| 非阻塞 I/O（轮询） | 同上，只是不睡 | 不挂起 |
| I/O 多路复用（select） | 同上：就绪后自己 `recv` | 等事件时挂起 |
| 信号驱动 I/O | 同上 | 不挂起 |
| **异步 I/O（AIO）** | 数据搬完才通知，用户不参与搬运 | 不挂起 |

**"同步"这个标签下，本来就既有阻塞、也有非阻塞。** 可见"同步 ≠ 阻塞"是教科书的标准划分，不是随口的说法。

## 3. 四个象限（重点）

| 象限 | 名字 | 含义 | 典型实现 | 谁在"等" |
|---|---|---|---|---|
| ① | **同步阻塞** | 结果自己等，线程被挂起 | 阻塞 socket 的 `read/recv`、`time.sleep`、`requests.get`、Java `InputStream.read` | 线程死等内核 |
| ② | **同步非阻塞** | 结果自己等，但每次尝试立即返回 | `sock.setblocking(False)` + `while` 轮询 | 应用自己反复问 |
| ③ | **异步阻塞** | 结果靠事件通知，但等待通知时线程阻塞 | `select` / `poll` / `epoll_wait` | 线程阻塞等"事件"，就绪后自己再读 |
| ④ | **异步非阻塞** | 结果和完成通知都由内核/事件循环负责，等待也不挂起 | Linux `io_uring` / POSIX `aio_read`；用户态的 `asyncio`（事件循环 + 非阻塞 I/O） | 谁都不用等，事件循环驱动 |

```
                线程不挂起                     线程挂起
结果自己等   ② 同步非阻塞（轮询）         ① 同步阻塞（死等）
结果被通知   ④ 异步非阻塞（事件循环）      ③ 异步阻塞（select/epoll）
```

### 3.1 为什么 ③ 叫"异步阻塞"——最反直觉的一格

`select([sock1, sock2], timeout)` 的行为是：

- 它在内核里**阻塞等待**（线程挂起）→ 所以是**阻塞**；
- 但它等的**不是某一个 I/O 的结果**，而是"**这些 fd 里任意一个就绪**"这个**事件**，就绪后它通知你（返回就绪列表），你再自己去 `read` → 所以"通知机制"是**异步**的。

经典术语叫"**I/O 多路复用**"：一个线程用 select/epoll 同时监视成百上千个 fd。**注意：就绪之后那次 `recv` 仍然是同步的**——select 只是帮你省去了"挨个试探"，并没有把 I/O 变成异步。真正的异步 I/O（内核把数据都搬完了再通知）需要 `io_uring`/AIO。

实测（本节验证脚本）：

```
select 一开始无事件 -> 阻塞等待，0.5s 后连接到来才返回: 0.50s, 就绪 1 个
accept 立即返回（事件已就绪）
```

线程确实被阻塞了 0.5 秒（挂起状态），但它是被"连接到来"这个**事件唤醒**的——这就是 ③ 的全部含义。

### 3.2 ④ 异步非阻塞：asyncio 的真实位置

`asyncio` 在用户态实现了 ④：

- 底层 socket 全部非阻塞（`setblocking(False)`）；
- 事件循环用 `select/epoll` 等事件（内部其实是 ③ 的动作）；
- 但对**程序员**暴露的是"**提交任务立即返回 Task，await 时让出控制权**"——从编程模型看是"异步非阻塞"。

**这也说明"同步/异步"首先是编程模型视角，"阻塞/非阻塞"是内核/线程状态视角。** 同一个 asyncio 程序，底层用着 ③ 的 `epoll_wait`，上层呈现为 ④ 的"谁都不等"。

## 4. 实测：同一件事的 5 种写法（Python 3.13）

任务：做 3 次"等 0.5 秒"的操作，看总耗时。

| 写法 | 实测总耗时 | 说明 |
|---|---|---|
| ① 同步阻塞串行 | **1.50s** | 3 × 0.5 秒逐个等 |
| ② 多线程（每线程内部仍同步阻塞） | **0.50s** | 3 个线程并行"同步阻塞"——并发靠线程，不靠异步 |
| ③ asyncio 真异步 | **0.56s** | 单线程，3 个协程同时等待 |
| ④ asyncio 里误用 `time.sleep` | **1.51s** | 一个协程阻塞，整个事件循环卡死 |
| ⑤ 事件循环被拖累的证据 | good 任务本应 **+0.50s** 完成，实测 **+1.00s**，总耗时 **1.00s** | 另一个协程 `time.sleep(1.0)` 阻塞期间，整个 loop 停摆 |

代码（可直接跑）：

```python
import time, threading, asyncio

def timing(label, fn):
    t = time.perf_counter(); fn(); print(f"{label:<32} {time.perf_counter()-t:.2f}s")

def sync_serial():
    for _ in range(3):
        time.sleep(0.5)

def threaded():                       # 多线程 = 并发，不是异步
    ts = [threading.Thread(target=time.sleep, args=(0.5,)) for _ in range(3)]
    [t.start() for t in ts]
    [t.join() for t in ts]

async def a_gather():
    await asyncio.gather(*[asyncio.sleep(0.5) for _ in range(3)])
def asyncio_ok(): asyncio.run(a_gather())

async def a_bad():
    for _ in range(3):
        time.sleep(0.5)               # 阻塞整个事件循环
def asyncio_bad(): asyncio.run(a_bad())

async def good_task():
    t0 = time.perf_counter()
    await asyncio.sleep(0.5)
    return f"good done at +{time.perf_counter()-t0:.2f}s"

async def bad_task():
    time.sleep(1.0)                   # 阻塞 1 秒，good_task 也被拖住
    return "bad done"

async def mixed():
    t0 = time.perf_counter()
    res = await asyncio.gather(good_task(), bad_task())
    print(res, f"总耗时 {time.perf_counter()-t0:.2f}s")

timing("1 同步阻塞（串行）", sync_serial)
timing("2 多线程（每线程仍同步阻塞）", threaded)
timing("3 asyncio 真异步（单线程）", asyncio_ok)
timing("4 asyncio 中误用 time.sleep", asyncio_bad)
asyncio.run(mixed())
```

**结论**：异步的收益全部来自"**等待期间让出控制权**"。一旦用同步阻塞调用堵住事件循环，asyncio 立刻退化成串行（1.51s 与 1.50s 几乎一样，异步白用了）。

## 5. 高频误区

### 误区零：同步必然阻塞

见 2.6 节的实测：同步只约束"结果由调用方自己获取"，等待方式可以是挂起等（阻塞），也可以是轮询（非阻塞）。0.5 秒内 114341 圈 vs 1 次调用的对比，就是"同步但不阻塞"的铁证。真正会让人误判的，是把"**逻辑上卡住了**"当成"**线程被挂起了**"。

### 误区一：异步 = 非阻塞

反例就是 ③：`select/epoll_wait` 是**异步通知 + 阻塞等待**的混合体。更准确的说法是：

- **"异步 I/O"强调完成通知**（数据就绪/搬完才通知）；
- **"非阻塞"强调调用立即返回**；
- 二者可以叠加，也可以分离。asyncio 的编程模型是"异步非阻塞"，但它的底层事件等待是阻塞的（③）。

### 误区二：多线程 = 异步

多线程是**并发手段**，不是**异步机制**。100 个线程，每个线程里依然是"发起调用→原地等→拿到返回值"的**同步阻塞**代码，只是别人在别的核上帮你并行等。实测 ② 0.50s 证明了它确实更快，但它**不是异步**——因为每个线程都在阻塞，而且线程是有成本的（栈、上下文切换、默认 40 个线程池上限）。

Java 里的对照更清楚：`new Thread(() -> blockingRead()).start()` 是"多线程 + 同步阻塞"；只有 `CompletableFuture.supplyAsync(...)` 那种"立即返回 future、稍后回调"才叫异步。

### 误区三：`await` 就等于自动异步

`await` 只是"**把控制权交给事件循环**"这个动作；如果被 await 的对象内部在阻塞（`time.sleep`、同步 requests、同步 DB 驱动），事件循环照样死。实测 ④ 与 ⑤ 就是铁证：

- ① asyncio 中误用 3 次 `time.sleep(0.5)` → 1.51s（与串行一样）
- ② 一个协程 `time.sleep(1.0)`，同时另一个协程只等 0.5s → 后者被拖到 +1.00s 才完成

### 附加误区：异步一定更快

异步只在 **I/O 密集**场景赢（等待多、计算少）。**CPU 密集**任务用 asyncio 反而更慢——单线程无法并行计算，还得加上协程切换开销。CPU 密集请用多进程（`multiprocessing` / `ProcessPoolExecutor`）。

## 6. Java 对照表

| Java 概念 | 对应象限 | 说明 |
|---|---|---|
| BIO（`InputStream.read`、`ServerSocket.accept`） | ① 同步阻塞 | 一连接一线程，线程死等 |
| NIO（`SocketChannel` 非阻塞 + `Selector`） | ③ 异步阻塞（多路复用） | Selector 阻塞等事件，一个线程管多个连接 |
| AIO（`AsynchronousSocketChannel`） | ④ 异步非阻塞 | 回调式，Linux 上实现不成熟 |
| `Future` / `CompletableFuture` | 异步（编程模型） | 立即返回凭据，`get()` 阻塞取结果 / 回调编排 |
| Netty | ③ 的工程化 | Reactor 模式：事件循环 + 非阻塞 channel |
| 虚拟线程（Loom, JDK 21） | "同步写法 + 非阻塞内核" | 线程便宜到可以"一请求一线程"，`read` 阻塞时把载体线程释放——**说明编程模型（同步）与内核状态（非阻塞）可以解耦** |

**这张表最值得记的一点**：Java 虚拟线程 = "你用同步阻塞的写法，运行时帮你把阻塞变成非阻塞"——这正是"两个维度可以自由组合"的最好例证。

## 7. 对 FastAPI 的意义（项目里每天都在用）

FastAPI 的调度规则直接由本章概念决定：

| 路由写法 | 执行位置 | 阻塞风险 |
|---|---|---|
| `async def` | **事件循环线程**（uvicorn 主 loop） | 里面出现同步阻塞调用 → **卡死整个服务** |
| `def` | 自动丢进**线程池**（anyio `to_thread`，默认约 40 线程） | 单个请求阻塞只占一个线程，不会卡 loop；但线程池满了会排队 |

```python
# ❌ 危险：async def 里用同步阻塞库
@app.get("/bad")
async def bad():
    time.sleep(3)                       # 3 秒内所有请求排队
    r = requests.get("https://example.com")   # 同理
    return {"ok": True}

# ✅ 正确：异步库
@app.get("/good")
async def good():
    await asyncio.sleep(3)              # 让出 loop，别的请求照常处理
    async with httpx.AsyncClient() as c:
        r = await c.get("https://example.com")
    return {"ok": True}

# ✅ 正确：同步库但用 def，或显式丢线程池
@app.get("/ok")
def ok():
    time.sleep(1)                       # FastAPI 自动放线程池
    return {"ok": True}
```

**记住一条**：`async def` 的门票是"里面所有调用都是非阻塞的"；有一个同步阻塞调用，就把整条事件循环堵死。

## 8. 使用场景速查

| 场景 | 该选什么 | 原因 |
|---|---|---|
| 大量网络请求（爬虫、网关、API 聚合） | asyncio / aiohttp / httpx | I/O 密集，等待占 90% 时间 |
| 数据库访问 | async 驱动（asyncpg、aiomysql） | 同上 |
| CPU 密集（图像处理、加解密、大数据计算） | 多进程 / `ProcessPoolExecutor` | 需要真并行，GIL 限制线程 |
| 少量并发、代码简单优先 | 多线程 + 同步阻塞 | 心智负担低，线程池兜底 |
| 万级并发连接 | 事件循环 + 非阻塞（Netty / asyncio） | 线程模型撑不住 |
| 阻塞库无法替换（老驱动） | `run_in_threadpool` / `to_thread` | 把阻塞隔离到线程池 |

## 9. 坑清单

1. **`async def` 里写 `time.sleep`**：整个 loop 停摆（实测 4 组数据证明）。
2. **把"多线程"说成"异步"**：概念错，线程池还有上限，高并发时线程耗尽一样排队。
3. **以为 select 是"异步所以不阻塞"**：select 恰恰阻塞；它异步的是"事件通知"。
4. **以为 `await` 一定快**：await 一个阻塞函数 = 阻塞整个 loop。
5. **CPU 密集硬上 asyncio**：单线程排队算，比同步还慢。
6. **异步代码里用同步锁/同步日志**：`threading.Lock` 等阻塞原语会卡 loop，应使用 `asyncio.Lock`。
7. **把"抢不到 GIL"当成"被阻塞"**：线程在 CPU 密集循环里争不到 GIL 是"可运行但拿不到执行权"，与被内核挂起（睡在 `recv`/`sleep` 上）是两种状态，排查手段不同（前者减线程/多进程，后者换异步/非阻塞）。
8. **说"socket 是阻塞的"**：准确说法是"阻塞模式 socket 上的调用会阻塞**调用线程**"；阻塞是**调用的行为**，主体是**线程**，不是对象属性。
9. **以为阻塞的是整个进程**：多数情况只掐住发起调用的线程；只有当进程里所有线程都阻塞（或单线程程序）时，才看起来像"整个进程停了"。

## 10. 一句话记忆

> **同步/异步看"结果谁送回来"（我自己等 vs 你通知我）；阻塞/非阻塞看"等的时候我能不能干别的"（线程挂起 vs 立即返回）。**
> 四格：自己等 + 挂起 = ① 同步阻塞；自己等 + 不挂起 = ② 同步非阻塞（轮询）；别人通知 + 挂起 = ③ 异步阻塞（select）；别人通知 + 不挂起 = ④ 异步非阻塞（io_uring / asyncio）。
> 最难记的 ③ 一句话：**"事件的通知是异步的，等待通知这个动作是阻塞的"**。
> 最容易被否掉的一句：**"同步必然阻塞"——同步只管结果谁拿，不管线程睡不睡；轮询就是同步但非阻塞。**
> 阻塞的主体：**是发起调用的那个线程（执行流）**，不是进程、函数或 socket；只有在单线程程序 / 单线程事件循环里，才会表现为"整个程序停住"。
